<summary>Reflection</summary>

Unary RPC adalah metode request-response sederhana di mana klien mengirim satu permintaan dan menerima satu respons (seperti `ProcessPayment`), cocok untuk operasi sekali jalan. Server streaming mengirim aliran data multipel dalam satu respons (seperti `GetTransactionHistory`) yang ideal untuk kasus pengambilan data dalam jumlah besar atau real-time updates. Bi-directional streaming (seperti `Chat`) memungkinkan klien dan server saling mengirim beberapa pesan secara bersamaan melalui satu koneksi, cocok untuk aplikasi interaktif seperti chat, collaborative editing, atau monitoring real-time di mana kedua belah pihak perlu komunikasi simultan.

Keamanan gRPC di Rust melibatkan tiga critical layers: autentikasi melalui TLS/SSL certificates dan tokens (JWT/OAuth), authorization melalui role-based access control (RBAC) untuk memvalidasi permission pengguna terhadap operasi tertentu, dan encryption of data in transit menggunakan HTTPS/TLS dan data at rest dengan hashing/encryption. Dalam konteks Rust, perlu implementasi proper error handling untuk menghindari information disclosure, input validation ketat terhadap payload protobuf untuk mencegah injection attacks, dan secure management konfigurasi credentials menggunakan environment variables atau secure vaults daripada hardcoding.

Tantangan utama dalam bi-directional streaming mencakup: manajemen concurrent message processing di mana multiple messages dari klien/server harus ditangani secara parallel, back-pressure handling untuk menghindari memory overflow ketika satu sisi memproduksi pesan lebih cepat dari yang dapat dikonsumsi, error handling dan recovery ketika koneksi putus di tengah streaming, dan synchronization/ordering guarantees terutama dalam aplikasi chat. Implementasi dengan tokio-stream dalam Rust memerlukan async task spawning dan channel communication yang diatur dengan baik untuk menghindari deadlocks dan race conditions.

`ReceiverStream` dari tokio menyediakan adapter elegan yang mengkonversi `tokio::sync::mpsc::Receiver` menjadi `Stream` yang compatible dengan tonic, memudahkan integrasi async producer-consumer pattern ke dalam gRPC responses. Keuntangannya termasuk: decoupling antara business logic dan gRPC layer, kemampuan untuk buffer pesan dengan configurable channel capacity (contoh: `mpsc::channel(4)` untuk transaction streaming), dan full async support dengan tokio runtime. Kerugiannya mencakup: potential memory overhead dari channel buffering jika tidak dikonfigurasi dengan optimal, kompleksitas dalam error handling, dan kesulitan dalam debugging message flow di production karena abstraksi layer tambahan.

Kode Rust gRPC dapat distruktur dengan: memisahkan business logic dari service implementations (contoh: create payment_service module terpisah yang dapat di-unit test), menggunakan trait-based architecture untuk mock dependencies dalam testing, membuat reusable utility functions untuk operasi umum seperti error handling dan logging, implementasi middleware layer untuk authentication dan logging, dan mengorganisasikan proto files secara hirarki dengan shared message types. Dalam proyek ini, `PaymentService`, `TransactionService`, dan `ChatService` dapat dipindahkan ke modul terpisah, membuat shared utility modules untuk streaming logic, dan menggunakan dependency injection pattern untuk meningkatkan testability.

Implementasi `MyPaymentService` saat ini hanya mengembalikan pesan yang hardcoded, namun untuk implementasi yang sesungguhnya perlu: persistent storage integration (database transactions untuk atomicity), payment gateway integration (Stripe, PayPal) dengan retry logic dan idempotency handling, validation logic untuk payment amount, user authentication, dan fraud detection, proper error handling dengan specific error codes, logging dan audit trails untuk compliance, dan async processing dengan message queues untuk long-running operations. Juga perlu implementasi circuit breaker pattern untuk external service calls dan compensation logic untuk rollback jika payment fails ditengah proses.

gRPC mengubah arsitektur distributed systems dengan enabling: efficient binary serialization melalui Protocol Buffers mengurangi latency dan bandwidth dibanding REST/JSON, true bidirectional streaming capabilities memungkinkan real-time applications yang sebelumnya memerlkukan WebSocket workarounds, HTTP/2 multiplexing untuk utilisasi koneksi yang lebih baik dan pengurangan overhead, language-agnostic service contracts melalui proto definitions mendorong standarisasi. Namun tantangan timbul karena: gRPC memerlukan HTTP/2 yang tidak disupport secara universal, berbeda dengan REST, integrasi dengan legacy systems memerlukan API gateways/adapters, dan observability tooling masih kurang dibanding ekosistem REST. Arsitektur menjadi lebih microservices-oriented dan event-driven, mempromosikan skalabilitas yang lebih baik tetapi menambah kompleksitas operasional.

HTTP/2 digunakan gRPC memberikan keuntungan: multiplexing multiple requests over single connection mengurangi latency, server push capabilities untuk proactive resource delivery, header compression dengan HPACK mengurangi overhead, binary framing lebih efficient dibanding HTTP/1.1's text-based. Dibanding WebSocket untuk real-time: HTTP/2 bidirectional streaming lebih efficient karena terintegrasi secara penuh ke transport layer tanpa menambah kompleksitas. Namun HTTP/1.1 masih relevan untuk kasus yang lebih sederhana dengan tool dan support yang lebih baik, WebSocket tetap lebih baik untuk sebagian skenario seperti browser-based applications karena universal browser support. HTTP/2's connection overhead juga lebih tinggi dibanding HTTP/1.1 untuk simple request-response patterns.

REST APIs menggunakan request-response model synchronous di mana client mengirim HTTP request dan menunggu response, secara fundamental terbatas untuk true real-time scenarios yang memerlukan multiple roundtrips atau polling, dengan latency inherent di setiap request-response cycle. gRPC's bidirectional streaming memungkinkan persistent connection dengan multiple messages yang datang asynchronously dari dua arah, memperbolehkan true real-time communication seperti di `ChatService` project ini. Responsivitas gRPC lebih baik untuk aplikasi yang membutuhkan sub-second latency karena HTTP/2 multiplexing mengeliminasi head-of-line blocking dan connection reuse. REST dapat diperbaiki dengan WebSocket upgrade, namun ini menambah kompleksitas, dimana gRPC's native support lebih elegan. Namun REST benefits dari caching (HTTP cache-control headers) dan synchronous model yang lebih simpel dan mudah dipahami, sedangkan gRPC's menukarkan kompleksitas untuk performa yang lebih baik.

Protocol Buffers di gRPC meng enforce schema contracts yang kuat di interface level, menyediakan: strict versioning dan backward/forward compatibility melalui penomoran, code generation melalui berbagai bahasa (Java, Python, Go, Rust, dll) mengurangi serialization bugs, payload size yang lebih kecil dibanding JSON sehingga bandwidth dan latency mengecil. Dibanding JSON's schema-less flexibility yang memperbolehkan penambahan tanpa merusak clients, Protocol Buffers memerlukan defisini schema yang jelas di depan yang bisa membatasi tetapi memastikan keamanan kontrak.
